# The owner's words behind the core: items 208 onward

How they are kept, and where each item lives: `archive/instructions.md`.

208. **14 November 2026** (the core; the first three quotes in a chat with a session the owner had asked to look
     through the core, not the design session, as that session quoted them on issue #237; the last two to the design
     session, in the message that asked for the queue to be built). Told that work in the core costs every project a
     sync and a reading, that five releases had been cut in two days where about one a week was meant, and shown what
     that session had found in the core:

     > We need to address everything you identified.

     Told that the core's open issues, about twenty, had no order though several waited on another:

     > I mean, you say we need a queue, should we have a queue with it all? And all the thijgs you've brought up?

     The owner agreed to a short file that holds the order alone, each line pointing to its issue, and to that
     session's advice that an orchestrator work the file while it holds items and be stopped once it is empty, with
     nothing released until then. Of a pause on new rules until the first batch was released:

     > And no pause. A pause is me not adding anything.

     To the design session, with the task of building it:

     > The open issues labelled `queued` and `by:chat` were filed today by a chat session I worked with. The decisions
     > quoted in them are mine; treat them as my word.

     > An orchestrator on Opus at high will work the whole file after you, rule changes included, building from those
     > issues. Write `AGENTS.md` and the file so that it can, and tell me plainly if any rule of the floor stands
     > against that.

     Behind "The queue" in `AGENTS.md` and the file `QUEUE.md`: the order in one file and the items in their issues, a
     line joined only on the owner's yes, an orchestrator while the file holds lines, one batch and then one release,
     and no pause written into any rule. Behind the builder who writes a queued rule from the owner's words on its
     issue, which is this repository's difference from `modules/inbox.md`, and behind the trusted builder in
     `SECURITY.md`: every file here is protected, so an orchestrator's builders could change none while that line named
     only the sessions the owner starts. The floor itself stood against none of it: a change to it or to the review
     guidelines still waits for the owner's yes in its pull request (floor rule 3), whoever builds it.

209. **14 November 2026** (the core, the same chat as the first quotes of item 208, as that session quoted it on issue
     #255). A builder session had opened a draft pull request here, pushed its commits with every check green, and
     stopped: this repository read neither `modules/work-flow.md` nor `modules/git.md`, so it held no rule for any step
     after the draft. Having said that everything established must hold in the core also, the owner proposed:

     > rule thar everything in agent-core must also abide by its own rules to the full extent, alongside all the
     > audits and refactoring it sets for others?

     Behind the two modules this repository reads at the start of every task since then (`AGENTS.md`, "The core this
     repository takes"), so that whoever builds here marks the pull request ready, asks for its reviews, fixes their
     findings and merges. The rest of what issue #255 asks is built from its line in `QUEUE.md`.

210. **14 November 2026** (the core, to the design session, while the pull request that built the queue waited for its
     checks). Told that the queue's rule left the release after a batch to the owner's word, so that an orchestrator
     would cut none:

     > When the queue holds no line a session can take and every check on main is green, start the release workflow.

     Behind the release of the first batch in "One batch, then one release" in `AGENTS.md`: the owner's word for it,
     given ahead, so the session that finds the file worked through starts the `release` workflow, which itself cuts
     nothing unless every check on `main`'s newest commit has passed. Read narrowly, as the word for the one release
     that follows `release-5`: the words could also stand for every batch, and a release once cut is never moved or
     deleted, so every later release waits for the owner's word again until the owner says otherwise.

211. **14 November 2026** (the core; the first three quotes in a chat with a session the owner works with, not the
     design session, as that session quoted them on issue #260; the last to the orchestrator, in the message that
     started it). Told that, as the queue was first built, three pull requests would stand open for a yes the owner had
     given by queueing their issues, that every release after the first would wait for the owner's word again, and
     that what the owner said through a chat session after that day would count as that session's own:

     > When something is queued, it is because I want it done. No waiting.

     > should do a cut everytime the queue is empty, it means it has implemented everything I want from it if there is
     > nothing left in issues to be queued also.

     > "by:chat" essentially means we. I very rarely bother to write directly. You sre my interface.

     Asked for that session's view on the stand-in queueing no idea here, the owner was told to keep it for new and
     changed rules, and did not change it. To the orchestrator:

     > My yes is given for every queued change, the floor and the review guidelines included, as its issue describes
     > it: quote this in those pull requests. Cut a release each time the queue is empty and main is green.

     Behind "Queued means wanted" in `AGENTS.md`, where the yes that queued an issue is the yes floor rule 3 asks for in
     its pull request, relayed word for word and covering the change as the issue describes it; behind the release in
     "One batch, then one release", now for every batch, which widens item 210; behind what the chat session records
     counting as the owner's word on any day, in "Whose words an issue holds"; and behind what joins the queue without
     the owner: a bug, a test, a check for a rule that already stands, a task the scheduled look opens and a small
     finding of an audit, while a new or changed rule still joins only on the owner's yes.
